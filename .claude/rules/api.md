# Règles API (api.legarec.fr)

- Référence détaillée (schéma, rôles PostgreSQL, chiffrement, clés, tests) : `docs/api.md`. Lots : `PLAN.md`.
- NestJS 12, TypeScript strict, validation de toutes les entrées par les schémas Zod de `packages/contracts`, réponses d'erreur uniformes (mêmes codes que les simulations), OpenAPI par `@nestjs/swagger` ; pas de `nestjs-zod`.
- **Cloisonnement** : toute requête concernant des dossiers, factures, documents ou paiements est filtrée par le créancier du compte connecté (rôle créancier) ou par les droits du rôle (équipe). Sécurité par ligne PostgreSQL activée et forcée sur toutes les tables ; toute table liée à un dossier porte `case_id` et `creditor_id` (clé étrangère composite). Test automatique obligatoire pour chaque route : un créancier ne peut jamais lire les données d'un autre ; une route absente de la matrice d'accès fait échouer `pnpm verifier`.
- Modules, routes, tables et colonnes en anglais (glossaire de `CLAUDE.md`) : `auth`, `creditors`, `debtors`, `cases`, `reminders`, `payment-plans`, `litigation`, `documents`, `emails`, `sms`, `calls`, `payments`, `remittances`, `ai`, `audit`, `settings`, `mailboxes`, et `account`, `members`, `delegations`, `vault`, `debtor-access`, `templates`.
- Rôles : Gestionnaire de créances, Responsable du recouvrement (unique), Directeur (unique), Développeur (unique), Créancier. Accès aux dossiers selon le rôle (Directeur : lecture de tous, actions sur les siens ; Responsable : ses dossiers, ceux des gestionnaires et les dossiers sans gestionnaire ; Gestionnaire : les siens ; Développeur : aucun). Délégations technique (Développeur) et administrative (Responsable). Paramètres techniques : Développeur et Directeur.
- Test automatique par route : chaque rôle n'accède qu'aux dossiers prévus, le Directeur ne modifie jamais un dossier qui ne lui est pas attribué, le Développeur ne lit aucun dossier.
- Comptes : même réponse et même travail pour un compte connu ou inconnu ; essai compté avant d'être vérifié ; limite par réseau, refus si Valkey est absent ; session relue à chaque requête, jeton changé après le second facteur ; lien tiré à l'envoi, usage unique, jamais écrit ; chaque action de support est dite au Directeur dans la même transaction. Seul `modules/auth` ouvre une transaction au nom d'un compte.
- Audit : journaliser qui, quoi, quand, pour le compte de qui, depuis quelle IP pour les actions sensibles (validation d'échéancier, export, modification de coordonnées, secrets, envois LRAR, procédures, boîtes OVH, délégations) et les consultations par le Directeur de dossiers qui ne lui sont pas attribués.
- Audit et historique en ajout seul (hors `legarec_retention`, par fonctions à durée fixe) : ni UPDATE, ni DELETE, ni TRUNCATE ; acteur et « pour le compte de » lus dans la session, jamais passés en paramètre ; ni nom, ni référence, ni code, ni secret dans l'audit : une action et des paramètres du catalogue `AUDIT_ACTIONS`, aucun texte libre.
- Prisma : migrations versionnées, appliquées par `src/migrate.ts` (jamais le moteur natif de Prisma) ; une requête = une transaction `Database.run(actor, fn)`, Prisma interdit ailleurs (ESLint) ; SQL brut limité à : séquences, verrous consultatifs, recherche trigramme, agrégats (`SET ROLE` et `set_config` dans `src/platform` seulement) ; index partiels, EXCLUDE, RLS et déclencheurs en SQL dans les migrations.
- Action qui engage : `@Commits()`, donc `Idempotency-Key`, et valeur attendue (montant, nombre, destinataire) ; 409 si l'état a changé depuis la confirmation. Chaque texte, chaque liste et chaque nombre d'un corps a un plafond (testé). Journal : message constant, le reste dans les champs d'une liste fermée.
- Tâches longues ou planifiées dans BullMQ sur Valkey (relances, envois groupés, synchronisation IMAP, reversements), jamais dans la requête HTTP. Aucun appel externe dans une transaction : table `outbox`, puis BullMQ ; une tâche ne porte que des identifiants, déclare de qui elle peut venir (`from`) et si elle peut être rejouée (`repeatable` ; jamais pour un courrier, un SMS ou un message de collaborateur) ; le worker l'exécute avec les droits de son auteur, relus, et n'agit au nom de l'application qu'après avoir vérifié son droit d'agir.
- Plafonds de contact : par débiteur, tous créanciers confondus, sur tous les envois et appels ; blocage, dérogation motivée du Responsable, ou du Directeur sur ses dossiers. Exemptés : réponse à un message reçu depuis moins de 7 jours, quittance, code demandé, avis de nouveau message. Premier courrier : lettre postale seulement ; aucune relance avant son envoi.
- **MySendingBox** : compte test par défaut ; production seulement si `MYSENDINGBOX_ENV=production` est explicitement défini. Ne jamais envoyer de vrai courrier depuis un test.
- Documents : modèles HTML Handlebars, PDF via Playwright. Fichier reçu : type réel vérifié, quarantaine jusqu'au résultat de ClamAV. Code d'accès retiré de tout message entrant ; copie sans code pour le créancier et pour qui ne peut pas agir sur le dossier. Valeur entre crochets dans un rendu : envoi refusé (`FIRM_INCOMPLETE`). Contrôles à l'import d'un modèle : champ inconnu, bloc imposé absent, script ou ressource externe → refus (liste des champs : `maquette/champs-de-fusion.json`).
- E-mails : kit `kits/emails-handlebars` copié sans réécriture dans `apps/api/templates/emails/`, plus `staff-message` ; `config` jamais en dur ; `case.access_code` transmis aux seules relances reminder-1 à reminder-3, jamais dans l'objet, une URL, un nom de fichier ni un journal ; ces relances exigent un SIREN (jamais pour un particulier) ; replyTo seulement pour reminder-1 à reminder-3. Messages des collaborateurs par SMTP OVH de leur boîte (mot de passe chiffré, `MAILBOX_SECRETS_KEY`), copie IMAP dans « Éléments envoyés », quota par boîte ; jamais de bascule vers Resend. recouvrement@ en réception seule.
- Boîtes OVH : API OVHcloud (appels signés, pas de paquet `ovh`) limitée à `/email/domain/legarec.fr/*` ; recouvrement@ protégée ; aucune suppression de boîte depuis l'application ; chaque action confirmée et journalisée.
- Paiement : chèque et virement uniquement, enregistrés à la main ; aucun prestataire de paiement, aucune donnée de carte. Montants en centimes entiers. Imputation : intérêts, puis principal de la facture la plus ancienne à la plus récente, puis indemnités ; un chèque impayé annule par écritures, jamais par effacement. Pas de 40 € pour un particulier, ni d'intérêts pour lui avant une mise en demeure.
- Secrets (Resend, OVH, MySendingBox, stockage S3 OVHcloud, 3CX, IA) : en production, saisis dans Paramètres techniques > Secrets (Développeur et Directeur), chiffrés en base, jamais réaffichés ni renvoyés par l'API ; mots de passe des boîtes OVH chiffrés en base. Hors de la base, dans un fichier du serveur : clé maîtresse du coffre, accès à PostgreSQL et à Valkey, clé de signature des sessions. En développement, `.env` temporaire à la racine, clés de test seulement, saisies par le cabinet et jamais lues par Claude Code ; aucune clé OVH ni 3CX (pas de mode test) ; tests et GitHub Actions toujours en simulé. Clés internes (`MAILBOX_SECRETS_KEY`, `ACCESS_CODE_KEY`, `LOOKUP_KEY`) tirées au hasard par l'API et rangées dans le coffre ; lues par `InternalKeys` dans la transaction ; un renouvellement garde les anciennes valeurs. Jamais dans le code, les logs, les fixtures ni GitHub Actions. Noms attendus : `docs/api.md`.
- Données personnelles : durées de conservation et anonymisation (voir `DECISIONS.md` : dossiers et historique 5 ans après clôture ; factures, quittances, paiements et reversements 10 ans ; enregistrements, transcriptions, SMS non rattachés et messages non vérifiés 6 mois ; journal d'audit et journal de l'IA 1 an ; imports non confirmés 30 jours).
- IA (`apps/api/src/ai`, couche fournisseur ; transcription après l'appel seulement) : sorties structurées validées par Zod, journal de chaque suggestion, contrôle du budget avant appel, minimisation des données, aucune action déclenchée sans validation humaine. Noms de modèles en variables d'environnement.
